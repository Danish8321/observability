Raksawi Telemetry Stack

Infra proposed Grafana, Loki and ClickHouse. This page checks that stack against what the screening services actually emit, recommends one addition we consider required, and lists the optional pieces with what each one buys.

The recommendation

Every service emits OpenTelemetry over OTLP (http/protobuf, port 4318) to one collector, which applies the attribute allowlist before anything is stored. Nothing below changes service code. The choice is only where each signal is stored and how it is read.

Loki for logs

Infra pickLogs

Indexes only a few labels and keeps the log text in compressed chunks on S3. Ingests OTLP natively at /otlp/v1/logs, so the collector needs no special exporter. We agree with this pick.

With it

Every log line from one screening workflow, across the API and the worker:

# LogQL · example correlation id
{service_name=~"screening-api|screening-worker"}
  | correlation_id = "3f2b8c1e9d7a4b6c8e0f1a2b3c4d5e6f"
  • The cheapest store per GB of the options, because the text is not indexed.
  • OTLP attributes are kept as structured metadata, so correlation_id filters without becoming an index label.
Watch out for
  • Full-text search over long windows is slow by design. Queries should start from a service and a time range, as the diagnostic specs do.
  • application.id must never become a Loki label: one label per applicant creates one stream each and degrades the store. Keep it as structured metadata, the same rule as for metric dimensions.

ClickHouse for traces

Infra pickTraces

A column store queried with SQL. The collector writes spans with its clickhouse exporter into an otel_traces table, and Grafana reads them through the ClickHouse plugin, which includes a trace viewer. We agree with this pick for traces.

With it

The incident question "how many screenings failed, how slow were they, and how many retried", in one query:

-- ClickHouse SQL · default exporter schema
SELECT toStartOfHour(Timestamp)          AS hour,
       countIf(StatusCode = 'Error')     AS failed,
       quantile(0.95)(Duration) / 1e9    AS p95_s,
       countIf(has(Events.Name, 'screening.retry')) AS retried
FROM otel_traces
WHERE ServiceName = 'screening-worker'
  AND SpanName = 'screen application'
  AND Timestamp > now() - INTERVAL 1 DAY
GROUP BY hour ORDER BY hour
  • Any span attribute can be filtered and aggregated, e.g. diagnostic query 2.7: WHERE SpanAttributes['application.id'] = '…'.
  • Apache 2.0 licence. Infra already plans to run it.
Watch out for
  • A ClickHouse cluster has to be operated: replication, ClickHouse Keeper, disk, and retention through table TTLs.
  • The table schema belongs to the exporter version. Pin the collector version and read the schema before writing dashboards against it.
  • Links from a log line or a metric to its trace have to be configured by hand in Grafana. With Tempo they come built in.

Alternative considered: Grafana Tempo. Tempo is cheaper (it stores only on S3) and links natively to Loki and Mimir, but it is weaker at ad-hoc aggregate questions like the one above. Both are good choices, and we accept Infra's.

Mimir for metrics

We add: requiredMetrics

A long-term Prometheus store on S3, queried with PromQL. Ingests OTLP at /otlp/v1/metrics. This is the one gap in the proposed stack: the plan's alerting, SLOs and NATS monitoring are all built in PromQL.

With it

Screening p95 and the abandoned-application alert, as standard PromQL:

# p95 screening time, seconds
histogram_quantile(0.95,
  sum by (le) (rate(screening_duration_seconds_bucket[5m])))

# alert: any application abandoned in 10 minutes
sum(increase(screening_applications_abandoned_total[10m])) > 0

# NATS: a consumer is falling behind
increase(gnatsd_varz_slow_consumers[5m]) > 0
  • The NATS exporter and the collector's own health metrics are already Prometheus-native, so their dashboards and alerts drop straight in.
  • Exemplars: click a spike in screening.duration and open the trace that caused it (plan D4).
  • Burn-rate SLO alerts (plan D10) are standard, well-tested PromQL patterns.
  • Runs the same way as Loki (same vendor, same S3 layout), so Infra operates one pattern, not two.
Without it (metrics in ClickHouse)

The same p95 becomes hand-written SQL over histogram buckets:

-- every panel and alert is written like this
SELECT toStartOfFiveMinutes(TimeUnix) AS t,
       arrayJoin(arrayZip(ExplicitBounds,
         arrayPopBack(BucketCounts))) AS b
       ... /* cumulative sum, rate, interpolation */
FROM otel_metrics_histogram
WHERE MetricName = 'screening.duration'
  • No PromQL, so no recording rules and none of the existing alert or dashboard libraries.
  • SLO burn-rate alerting has to be built from scratch.
  • The collector's ClickHouse exporter is less mature for metrics than for traces and logs.

Alternatives considered. VictoriaMetrics (Apache 2.0) is simpler and lighter to run, but its exemplar support is uncertain, and plan D4 needs exemplars. Prometheus alone keeps data on local disk, which does not suit long retention.

Tail sampling

We add: requiredTraces

A processor in the collector, not a new package. It decides what to keep once a whole trace has arrived, so it can keep every trace that matters and sample the rest (plan D4, ADR-0039).

With it 
# collector · tail_sampling policies
- name: errors
  type: status_code
  status_code: { status_codes: [ERROR] }
- name: slow-screening
  type: latency
  latency: { threshold_ms: 2000 }
- name: baseline
  type: probabilistic
  probabilistic: { sampling_percentage: 10 }
  • Every failed or abandoned screening is kept at 100%, at about a tenth of the storage.
Without it
  • Either every trace is stored, so ClickHouse grows linearly with traffic, or head sampling keeps a random 10% and drops 90% of the failures you would investigate.
  • Cost of having it: with more than one collector replica, spans of one trace must reach the same replica, which means a load-balancing exporter tier in front.

Blackbox exporter

We add: recommendedMetrics

Probes endpoints from outside the service and reports up/down and latency as metrics.

With it 
# alert: screening-api health check failing
probe_success{job="blackbox", instance="screening-api"} == 0
  • Catches the failure that sends no telemetry at all: a crashed service. This powers plan D11's freshness probe.
  • Small: one container and a list of targets.
Without it
  • If the worker dies, screening_applications_abandoned_total stays flat at zero, which looks perfectly healthy. Only the absence of data reveals it, and absence is easy to miss.

Pyroscope

LaterProfiles

Continuous CPU and memory profiling, linked from a slow span to the code that was running.

With it

illustration The trace shows screen application spending 3s inside the worker with no child spans. The profile for that window shows which method was burning the time.

Without it
  • Traces show where time went, but not why inside one process.
  • Cost: a .NET profiler agent (roughly 2–5% overhead) and a fourth store. Revisit once logs, traces and metrics are in production.

Not recommended

OptionWhy not
No Metrics in ClickHouseLoses PromQL, recording rules and SLO tooling; see the Mimir section above.
No Grafana OnCall OSSIn maintenance mode and being archived. Use Grafana alerting with email, Slack or a webhook.
No Jaeger UI, separate AlertmanagerDuplicates what Grafana already does.
No SigNoz in productionOur current demo backend. It is ClickHouse plus its own UI, so it competes with Grafana instead of adding to it.

Trade-off to accept

Traces in ClickHouse and metrics in Mimir means Grafana's jumps between signals are configured, not built in. It is a one-off cost of a few settings: a Loki derived field turning trace_id into a link to the ClickHouse data source, and Mimir exemplars pointing at the same data source.

Questions for Infra

  1. Is ClickHouse for traces only, or did you also intend it for metrics or logs?
  2. Will you run Mimir (or another PromQL store) for metrics?
  3. Who runs the OpenTelemetry collector, and will it run our allowlist policy file unmodified? It is one of our three enforcement points (ADR-0009).
  4. Alert delivery: SES, another SMTP relay, or a paging tool?
  5. Do you want dashboards and alert rules from us as files (Grafana JSON and YAML), or will you build them?
  6. Retention for each signal, and do you want the blackbox exporter and Pyroscope?
